# Security: database RPC surface

Exos's browser client talks to Postgres through PostgREST, so every function
that `anon` or `authenticated` may EXECUTE is callable as
`POST /rest/v1/rpc/<name>`. Most Exos logic runs in `SECURITY DEFINER`
functions (they bypass RLS), so each one has to check who is calling.

This page records the audit of the Supabase security advisor findings for
Exos on the shared project (2026-09-28), what
`supabase/migrations/20260929080000_exos_rpc_hardening.sql` changed, and the
settings an operator has to change in the dashboard because code can't.

The tests are in `tests/exos/test_rpc_hardening.sql` (wired into
`tests/exos/run_p0.sh`). H3 in that file fails if a new anon-callable definer
function appears outside the intended public set, so an addition has to be
reviewed and added to its allowlist.

## Rules for new functions

- Every `SECURITY DEFINER` function sets `SET search_path = public, pg_temp`
  (test H1 checks all of them).
- `REVOKE ALL ... FROM PUBLIC, anon, authenticated`, then grant only the roles
  that call it. Helpers used only by other definer functions, definer views,
  cron jobs or edge functions (service role) get no client grant.
- A client-callable function checks the caller first: `auth.uid()` for
  self-service, `exos_has_org_role(...)` or `exos_can_door_event(...)` for
  staff actions, a bearer token for links. Look the row up, then check the
  caller against *that row's* org or owner, never against an id the caller
  passed in.
- Anon writes must be gated by an unguessable token (`gen_random_uuid()` or
  more) or rate-limited (`exos_rate_hit`, `exos_voucher_throttle`).
- Don't return emails or phone numbers except to org staff who need them
  (mask with `exos_mask_email` / `exos_rr_mask_email` otherwise).

## Verdicts

Legend: **OK** = intended and properly checked; **Revoked** = internal helper,
client EXECUTE removed; **Fixed** = body patched in 20260929080000.

### Partner API writes (exos_api_write)

The partner API (`exos-api`, service role) writes through one definer
function, `exos_api_write(key, action, target, args, idempotency_key)`
(mig 20261031110000; service_role only, its `_exos_api_*` helpers no grant at
all). It loads the API key (not revoked), re-checks the key's scope for the
action, and requires the key's creator to still be an active member of the
key's org. It then sets the transaction's JWT claims (`request.jwt.claims`,
`request.jwt.claim.sub` / `role` / `email`) to that member, so `auth.uid()`
inside the dashboard's RPCs is the creator and their role *now* decides, and
puts the previous claims back before returning. Every target (event, ticket
type, order, ticket, list, guest, item) is pinned to the key's org before any
RPC runs, so a creator who is staff of several orgs, or a platform admin,
can't reach another org through a key. Table writes the dashboard does under
RLS (events, ticket types, add-ons, POS items) check the same roles as the
policy and write only whitelisted columns; server-owned columns are refused.
Each write is logged in `exos_api_writes` (owner / manager can read their
org's rows); refunds and comps are flagged `money_moving`. Tests:
`tests/exos/test_core_api.sql` (C1-C16), races: `tests/exos/race_core_api.sh`.

### The fan API and account tokens (mig 20261105110000)

`exos-api` `/v1/me/…` (docs/api/me.json) acts for the token's own user. One
service-role function, `exos_api_me(token_hash, kind, action, target, args)`,
re-resolves the bearer from its hash (`exos_api_token_auth`, then
`exos_api_account_token_auth`), so only a personal access token, an account
token or an OAuth token has a user; an org API key's hash, a revoked or
expired token or a member who left is 42501. It checks `me:read` / `me:write`
(a `:write` covers its `:read`; the legacy `read` never covers `me:read`), sets
the request claims to that user, calls the app's own signed-in RPC
(`exos_bulk_create_transfers`, `exos_cancel_transfer`, `exos_claim_transfer`,
`exos_ask_refund`, `exos_my_*`, `exos_wallet_*`, `exos_set_marketing_emails`,
`exos_create_personal_token`, …) and puts the claims back. Points to review:

- **User scopes.** `me:read` / `me:write` are in every role's token default
  (`exos_role_token_scopes`) and never an org API key's: trigger
  `exos_api_keys_no_user_scopes` refuses them on `exos_api_keys`, and
  `_exos_tg_org_role_scopes` drops them from a role's org-configured set (they
  are the user's, not the org's to set).
- **Isolation.** Every row is filtered by the token's user id in SQL: tickets
  by `owner_id`, orders by `buyer_uid`, transfers by sender (or a pending one
  addressed to the user's confirmed email), refund requests and memberships
  through the user's own RPCs. Another user's id answers 404, as one that
  doesn't exist. An order's default transfer / refund set is the tickets the
  user still holds.
- **Barcodes.** Ticket detail carries the live 30-second code
  (`T-<ticket>:<owner>:<bucket>:<mac>`, `_exos_door_code_mac` with the day key,
  as the app and `exos_ticket_link_view`), only for an active ticket the user
  holds, of an event not cancelled, not in a pending transfer. Lists never
  carry a code; nothing returns `barcode_secret`. Wallet passes go through
  `exos_wallet_issue_pass` / `exos_wallet_season_pass` (same transfer lock).
- **Tokens from tokens.** Only a personal or account token (never an OAuth
  app) lists, mints or revokes the user's tokens; a new one gets at most the
  maker's effective scopes and never outlives it (its `expires_at` is clamped
  to the maker's), a personal token mints only for its own org (and
  `exos_create_personal_token`'s role rules hold), an account token only
  account tokens.
- **Account tokens** (`exos_account_tokens`): `exos_pat_…`, SHA-256 at rest,
  shown once, for a user with no organization, `me:*` only (CHECK and the
  create RPC), at most 10 active, 30 / 90 / 365 days or none, email confirmed
  first. RLS: the user reads their own rows; no column grant on `key_hash`;
  writes through `exos_create_account_token` / `exos_revoke_account_token`
  (authenticated, `auth.uid()`) and `_exos_account_token_revoke_self`
  (service role: `DELETE /v1/personal-access-tokens/current`). exos-api lets
  an account token call `/v1/me/…`, `GET /v1/me` and that revoke only.

The same migration's org writes (`exos_api_gap_write`: series, fee rules, API
keys, orphaned seats, imported attendees, membership scans and gifts, gift
card issue, offline donations) follow `exos_api_write`'s pattern below, with
the key's effective scopes (`_exos_api_key_scopes`) and its creator's live
role per action (`_exos_api_gap_action_roles` → `_exos_api_key_actor`; API
keys: owner only, never above the making key's scopes, never a user scope,
the new key's plaintext returned once and never logged). Every target is
pinned to the key's org first. Tests: `tests/exos/test_fan_api.sql` (FA1-FA10).

### Organizer-controlled access (mig 20261104180000)

Per-role API permissions, venue booking requests with event-scoped grants,
and the partner presale setting (docs/org-access.md). Nothing is granted to
anon. Signed-in RPCs (`exos_org_role_scopes_get` / `_set` / `_reset`,
`exos_venue_directory`, `exos_venue_request_create` / `_decide`,
`exos_venue_requests`, `exos_partner_grants`, `exos_partner_grant_set` /
`_revoke`, `exos_cohost_events`, `exos_partner_presale_get` / `_set`,
`exos_event_partner_presale_set`) check the caller's live role in the org they
act for; the `_exos_*` cores are service-role only (exos-api passes the key's
org; writes need a key whose creator holds the role now,
`_exos_api_key_actor`). Points to review:

- **Scopes are computed at request time.** `exos_api_key_auth` (exos-api,
  exos-mcp) and the three API write functions read `_exos_api_key_scopes`:
  the key's stored scopes narrowed to its creator's live role's set in the
  org. Tokens go through the patched `exos_api_token_auth`. Lowering a role
  is enforced on the next request, never only at creation. The set can't
  exceed `exos_role_scope_ceiling(role)` (a trigger on
  `exos_org_role_scopes` enforces it for every writer, the service role
  included); only the owner may change it.
- **The venue gate** (`_exos_venue_gate`) runs inside the event, hold-night
  and event-template write paths, so the dashboard, the API and templates
  answer alike. Its refusal names only the venue id the caller already sent.
  `owned` is self-declared, so nothing links a promoter's record to an owned
  venue but the promoter itself (`exos_venue_link`); name matches are only
  suggestions, ambiguous ones shown as such, with `verified` as a hint.
  `verified` is set only by a platform admin (`exos_admin_set_venue_verified`,
  which sets the transaction-local `exos.venue_verify` for its own update);
  the trigger never trusts a bare service-role caller, because exos-api runs
  org API-key writes as the service role. Any other edit of the venue's
  name, address, relationship or org clears it, and exos-api drops
  `verified` / `listed_venue_id` from venue bodies. Suggestions and links see only venues the
  directory shows (`accepts_requests`); a refused link says nothing about
  the target. A squatter's "owned" venue gates no one else.
- **Grants**: a co-host reads or writes another org's event only through the
  `_exos_cohost_*` functions, which require a live grant with the scope
  (revoked: `P0002`, as for an event that doesn't exist, so ids can't be
  probed) and touch whitelisted copy fields only. A grant can never carry
  refunds; the venue directory never shows contacts or notes. Money
  (`gross_cents`) needs `finance:read` in the grant and in the caller's
  credential (`p_cred_scopes`, the effective scopes). Co-host edits run as
  the grantee key's creator (owner / manager now, `_exos_api_key_actor` in
  the SQL) and are logged in `exos_cohost_event_edits`.

### Printed tickets, team switching, Tixel (mig 20261105120000)

Nothing new is granted to anon. Points to review:

- **Print codes are door credentials.** 128 random bits, shown once, stored as
  SHA-256 only; never in `exos_api_writes` (the log keeps ticket ids and
  counts). One live code a ticket (partial unique index); while live, the
  ticket's `T-` / `W-` codes are refused, so a paper and a phone can't both
  admit. The door spends it in the same transaction as the ticket (a row
  update `WHERE status = 'active'`), and a trigger spends or voids it on any
  other admission, transfer, refund / release / void or secret change.
  Door phones get only its hash (`p` in the door keys). A print is never
  replayed from an Idempotency-Key; print answers are `no-store`, the HTML
  page has no script and a `default-src 'none'` CSP. Races:
  `tests/exos/race_print_codes.sh`.
- **`X-Exos-Org`** (`exos_api_token_auth_org`, service role): opt-in per
  personal access token (`multi_org`, chosen at creation, fixed by trigger
  `exos_personal_tokens_multi_org`; existing tokens are pinned and get 403
  `token_pinned_to_org`). An opt-in token acts in another org only while its
  user is an active member there, at the role there (the same narrowing as a
  token made in that org). OAuth tokens never switch (consent was for one org); an org API
  key naming another org is refused. The token's revocation still follows
  its home org (leaving the home org revokes it everywhere).
  An account token (mig 20261105110000) has no org at all:
  `exos_api_token_auth_org` returns nothing for it and exos-api answers 403
  `account_no_org` when it names one; a token minted through
  `POST /v1/me/personal-access-tokens` is always pinned, even from an opt-in
  parent (`tests/exos/test_wave3_integration.sql` W2, W3).
- **`exos-tixel-webhook`** is public (no JWT). The secret in `X-Secret` is
  compared in constant time against `EXOS_TIXEL_WEBHOOK_SECRETS` (an env
  var, 16+ characters a secret, one org each); unset = 404. It writes only
  through `_exos_tixel_ingest` (service role): a waitlist row for the one
  upcoming published event of that org with the Tixel title, never consent,
  never another org. 32 KB bodies, 120 a minute per org; nothing is sent to
  Tixel.

### Buyer location and genres (mig 20261106140000)

Nothing new is granted to anon. Points to review:

- **Buyer location is personal data, kept small.** `exos_order_locations`
  holds country, region, city and postal code of the billing address Stripe
  (Checkout `customer_details.address`, else the charge's billing address or
  card country) or PayPal (the payer's address in the capture response) gave
  at payment. Never a street (the table has no column for one), never an IP
  lookup. Written only by `exos_record_order_location` (service role:
  stripe-webhook, exos-paypal), which re-cleans every value, skips free and
  unpaid orders and closed accounts, and keeps the first location an order
  gets. RLS: the org's owner / manager / finance, and the buyer for their own
  order (through `exos_checkout_sessions.buyer_uid`); no client writes.
- **Erasure.** `exos_delete_my_account` deletes the locations of the caller's
  own orders and of guest orders under their **confirmed** email, before any

- **Reports aggregate.** `exos_event_buyer_geo` / `exos_org_buyer_geo`

  and `/v1/buyer-locations`, `orders:read`) return counts and gross per

- **Genres.** `_exos_org_event_ids_by_genre` and `_exos_org_genres` are

  `genres.list` action and a genres filter inside `exos_api_public` /

### Fee log, add-on entry codes, conditional questions (mig 20261107110000)

Nothing new is granted to anon (H3 unchanged). Points to review:

- **The fee log is append-only.** `exos_fee_adjustments` refuses UPDATE,
  DELETE and TRUNCATE in a trigger, for its owner and the service role too;
  only a foreign-key cascade (deleting the org, the event or the order)
  removes rows. RLS: owner / manager / finance of the org read; no client
  insert. Writers: `exos_record_refund` (marker `exos: fee adjustments`,
  through `_exos_fee_adj_sync_refunds`, under the order's row lock, so a
  retried or concurrent refund logs the right total once) and
  `exos_fee_adjustment_record` (authenticated; owner / manager / finance of
  the order's org, else 42501; a note, an idempotency key, the order's net
  fees never below zero). It records; it moves no money. The API reads it
  with `orders:read` (one order) or `finance:read` (an event), scoped to the
  key's org; another org's id is a 404 with nothing echoed.
- **Add-on entry codes keep the ticket's secret rules.** Each
  `exos_addon_passes` row has its own `barcode_secret`, which no client
  column grant covers: the holder gets it from `exos_my_addon_passes`
  (authenticated, own passes only, none once voided); door staff get day
  keys only from `exos_event_addon_passes` (owner / manager / scanner who may
  work the event, else 42501). A new owner (proof of email, guest claim)
  rotates the secret. Scans go through `exos_check_in_ticket` (marker
  `exos: addon pass codes`) into `_exos_check_in_addon_pass` (service role
  only), which checks the scanner's org role (42501 otherwise), the event,
  the code (day-key MAC, owner, bucket window) and the list before anything
  is written; a typed pass id is an owner / manager override with a reason,
  as for tickets. A ticket at an add-on-only list is refused in
  `_exos_checkin_list_refusal` (marker `exos: addon lists`), and an offline
  replay refused that way records a reject only, never a forced entry.
- **Conditional questions add no read surface.** The condition rides in the
  questions the public RPC already returns. A parent must be one of the same
  event's questions; a parent id from another event or org is refused
  without echoing its label. Hidden answers are dropped server-side
  (`_exos_validate_answers_core`, markers `exos: conditional questions 1..4`).

### SECURITY DEFINER views (8, by design)

`exos_public_*` are column projections of published rows for buyers; they run
as their owner so anon needs no grant on the base tables or the tax helpers.
`exos_ticket_barcode_secrets` and `exos_ticket_buyer_emails` filter rows
internally (`exos_can_read_ticket_secret`, `exos_has_org_role`). Since mig

them to `security_invoker` to quiet the advisor: anon would then need SELECT
on the base tables and EXECUTE on the helpers revoked above, which is exactly
what these views avoid.

## Operator settings (dashboard, not code)

These can't be set from a migration. Project: the shared Supabase project
(`hzrizjeaxlqcxfrtczpq`), so they also affect Terminal-2's users.

| Setting | Where | Recommendation |
|---|---|---|
| Leaked password protection | Authentication → Attack Protection (Password security) | Turn on: rejects passwords found in HaveIBeenPwned. The advisor flags it as off |
| Minimum password length and strength | Authentication → Sign In / Providers → Email | At least 8 characters with mixed character classes |
| Confirm email | Authentication → Sign In / Providers → Email | Keep on. Holds, waitlist, transfers and invites rely on `email_confirmed_at` |
| MFA (TOTP, optionally phone) | Authentication → Multi-Factor | Enable TOTP so org owners and finance can enrol. RLS doesn't require AAL2 yet; requiring it for owner / finance actions is a code follow-up |
| CAPTCHA on sign-up / sign-in / password reset | Authentication → Attack Protection | Turn on (Turnstile or hCaptcha). The voucher throttle and mail limits are per account, so cheap account farming weakens them |
| Auth rate limits | Authentication → Rate Limits | Keep the defaults or lower them for sign-up and OTP emails |
| Custom SMTP | Authentication → Emails → SMTP | Use the transactional provider so auth mail isn't capped by the built-in sender |
| JWT expiry | Project Settings → JWT / API | 3600 s (default) or less |
| Postgres upgrades | Project Settings → Infrastructure | Apply security patch releases when the advisor reports one |
